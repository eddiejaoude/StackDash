# Hosted instance runbook

Steps only Eddie performs on the hosted StackDash instance. This folder stays in the repository and is never published at `/docs` (`src/lib/docs.ts` skips `docs/internal/`). The deployment itself is described for any operator in [Deploy to Vercel and Supabase](../operations/deploy.md); this page adds who does what on the hosted instance.

Agents prepare configuration and preview deployments. They never trigger or promote a production deployment.

## Promote production (Eddie)

1. Merge to `main` after CI passes and the preview has been checked. Vercel builds a production deployment.
2. Before the deployment receives traffic, apply any new migrations ([Deploy, step 2](../operations/deploy.md#2-apply-the-migrations-forward-only)).
3. Promote or confirm the production deployment in Vercel.
4. Run the checks in [Deploy, verify the production deployment](../operations/deploy.md#8-verify-the-production-deployment).

## Hosted OAuth apps

The hosted instance has one registration per app ([OAuth apps](../operations/oauth-apps.md)), owned by the StackDash account or organization, with callbacks on the production origin. Eddie registers each one and enters its secrets in Vercel. Hosted users connect through these apps and never create their own.

- Keeping code scanning merge protection on. The **Protect main** ruleset has a `code_scanning` rule for the tool `CodeQL`, with security alerts set to `high_or_higher` and alerts set to `errors`. GitHub's [code scanning merge protection](https://docs.github.com/en/code-security/concepts/code-scanning/merge-protection) page lists three conditions that block a pull request: CodeQL reports an alert on its changed lines at security severity high or critical, or at severity error; the CodeQL analysis is still running; or CodeQL is not configured for the repository. Going by those docs the rule fails closed: if `.github/workflows/codeql.yml` stops reporting for a pull request, because the workflow is disabled or a path filter skips it, the pull request stays blocked rather than merging unscanned (read from the docs, not tested by disabling the workflow). A pull request blocked by code scanning with no alert on it means CodeQL did not report for it. The rule reads the results that `codeql.yml` uploads from the `CodeQL (actions)` and `CodeQL (javascript-typescript)` jobs, so it depends on that workflow staying on and on CodeQL default setup staying off (see "Keeping CodeQL default setup off" above). It is not a status check and is not one of the required checks. Dismiss a false positive with a reason, from the alert's annotation on the pull request (**Conversation** or **Files changed** tab, as [triaging alerts in pull requests](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts/triage-alerts-in-pull-requests) describes) or from the **Security and quality** tab for an alert already on `main`. The tab lists only `main`'s alerts by default, so an alert that exists only on a pull request is not there. Never loosen the thresholds instead (`high_or_higher` to `critical`, or `errors` to `none`): that lets every alert at the dropped severity through, not only the false one. On 2026-11-17, before the rule was added, the three open alerts on `main` were dismissed that way: one false positive in `src/lib/api/keys.ts` and two used in tests. Check the rule with `gh api repos/eddiejaoude/StackDash/rules/branches/main --jq '.[] | select(.type == "code_scanning") | .parameters'`: it must show `{"code_scanning_tools":[{"alerts_threshold":"errors","security_alerts_threshold":"high_or_higher","tool":"CodeQL"}]}` (it did on 2026-11-17). Check the workflow with `gh api repos/eddiejaoude/StackDash/actions/workflows --jq '.workflows[] | {name, state}'`: CodeQL must show `"state": "active"` (it did on 2026-11-17). If it shows anything other than `active`, run `gh workflow enable codeql.yml -R eddiejaoude/StackDash`. `disabled_manually` means someone turned it off. `disabled_inactivity` means GitHub did: in a public repository it disables a scheduled workflow after 60 days without repository activity ([disabling and enabling a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)), and `codeql.yml` has a weekly schedule.
