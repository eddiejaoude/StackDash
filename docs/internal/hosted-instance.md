# Hosted instance runbook

Steps only Eddie performs on the hosted StackDash instance. This folder stays in the repository and is never published at `/docs` (`src/lib/docs.ts` skips `docs/internal/`). The deployment itself is described for any operator in [Deploy to Vercel and Supabase](../operations/deploy.md); this page adds who does what on the hosted instance.

Agents prepare configuration and preview deployments. They never trigger or promote a production deployment.

## Promote production (Eddie)

1. Merge to `main` after CI passes and the preview has been checked. Vercel builds a production deployment.
2. Before the deployment receives traffic, apply any new migrations ([Deploy, step 2](../operations/deploy.md#2-apply-the-migrations-forward-only)).
3. Promote or confirm the production deployment in Vercel.
4. Run the checks in [Deploy, verify the production deployment](../operations/deploy.md#8-verify-the-production-deployment).

## Hosted OAuth apps

The hosted instance has one registration per app ([OAuth apps](../operations/oauth-apps.md)), owned by the StackDash account or organization, with callbacks on the production origin. Eddie registers each one and enters its secrets in Vercel. Hosted users connect through these apps and never create their own.

## What stays Eddie's

- Creating the Vercel project, the production (and staging) Supabase projects, and the SMTP sender.
- Registering the sign-in OAuth app and one app per provider ([OAuth apps](../operations/oauth-apps.md)), and entering their secrets.
- Generating and storing the production secrets.
- Setting the operator variables in the hosted instance's production environment ([Deploy, environment variables](../operations/deploy.md#environment-variables)): `STACKDASH_OPERATOR_NAME` is `Eddie Jaoude`, `STACKDASH_OPERATOR_EMAIL` is `eddie@jaoudestudios.com`, and `STACKDASH_GOVERNING_LAW` is `England and Wales`.
- Running migrations against production, registering the cron job, and inviting testers.
- Promoting production deployments. Agents never trigger or promote one.
- Migrating and rotating the JWT signing keys of the production (and staging) Supabase projects ([JWT signing keys](../operations/deploy.md#jwt-signing-keys)).
- Keeping the repository's security settings on. Since the repository went public on 2026-11-15, these are enabled: secret scanning, push protection, private vulnerability reporting (the route `SECURITY.md` names), Dependabot alerts, and Dependabot security updates. Two secret scanning settings stay off because they cannot be turned on here: scanning for non-provider patterns (GitHub's docs now call them [generic patterns](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/detect-secret-leaks/enabling-secret-scanning-for-generic-patterns)) and [validity checks](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/customize-leak-detection/enable-validity-checks). GitHub offers both only to organization-owned repositories with GitHub Secret Protection, and `eddiejaoude/StackDash` is owned by a user. On 2026-11-17 a `PATCH repos/eddiejaoude/StackDash` setting both to `enabled` returned 200 and both still read `disabled`, so trying again changes nothing until the repository moves to such an organization. Check them with `gh api repos/eddiejaoude/StackDash --jq '.security_and_analysis'` (`secret_scanning`, `secret_scanning_push_protection`, and `dependabot_security_updates` must show `"status": "enabled"`, and `secret_scanning_non_provider_patterns` and `secret_scanning_validity_checks` show `"status": "disabled"`), `gh api repos/eddiejaoude/StackDash/private-vulnerability-reporting` (`"enabled": true`), and `gh api -i repos/eddiejaoude/StackDash/vulnerability-alerts` (`204 No Content`).
- Making `main` the default branch, then keeping it so. The decision is on #461. Dependabot alerts and security updates read the default branch only, and so do the community profile and the issue chooser. On 2026-11-15 the default branch was `438-stackdash-placeholder`, so `main`'s dependencies were not covered. Check with `gh api repos/eddiejaoude/StackDash --jq .default_branch`: it must show `main` before `main` counts as covered.
- Keeping `main` protected. The **Protect main** ruleset (id `27309027`) blocks deleting and force pushing `main`, requires a pull request merged by squash, and requires four checks, which are the job `name:` values in `.github/workflows/ci.yml`: `Typecheck, lint, unit tests, build, audit`, `Secret scan (full history)`, `Database lint, types, and tests`, and `End-to-end tests (Chromium)`. Renaming a job leaves a required check that never reports, so change the ruleset in the same pull request as the rename. Repository admins can bypass the ruleset only when merging a pull request. Check that it applies to `main` with `gh api repos/eddiejaoude/StackDash/rules/branches/main --jq '.[].type'` (must list `deletion`, `non_fast_forward`, `pull_request`, `required_status_checks`, and `code_scanning`), and check its settings with `gh api repos/eddiejaoude/StackDash/rulesets/27309027 --jq '{enforcement, bypass: [.bypass_actors[] | "\(.actor_type) \(.actor_id) \(.bypass_mode)"], merge: (.rules[] | select(.type == "pull_request") | .parameters.allowed_merge_methods), checks: [.rules[] | select(.type == "required_status_checks") | .parameters.required_status_checks[].context]}'`: it must show `"enforcement":"active"`, `"bypass":["RepositoryRole 5 pull_request"]`, `"merge":["squash"]`, and the four checks.
- Keeping CodeQL default setup off. `.github/workflows/codeql.yml` is an advanced setup, and GitHub does not process advanced setup results while default setup is on. Check with `gh api repos/eddiejaoude/StackDash/code-scanning/default-setup --jq .state`: it must show `not-configured` (it did on 2026-11-16).
- Adding `Dependency review` to the **Protect main** required checks once `.github/workflows/dependency-review.yml` is on `main`. Issue #21 decided that dependency review blocks a pull request that adds a vulnerable dependency, and until the check is required a red `Dependency review` can still be merged. The order matters for the reason the ruleset bullet above gives for renames: a required check that never reports blocks every open pull request whose branch predates the workflow, so those branches need `main` merged in first. Check with `gh api repos/eddiejaoude/StackDash/rules/branches/main --jq '.[] | select(.type == "required_status_checks") | .parameters.required_status_checks[].context'`: it must list `Dependency review` (on 2026-11-16 it did not).
- Keeping code scanning merge protection on. The **Protect main** ruleset has a `code_scanning` rule for the tool `CodeQL`, with security alerts set to `high_or_higher` and alerts set to `errors`. A pull request cannot merge while CodeQL reports an alert on its changed lines at security severity high or critical, or at severity error, and it also waits while the analysis is still running ([code scanning merge protection](https://docs.github.com/en/code-security/concepts/code-scanning/merge-protection)). The rule reads the results that `.github/workflows/codeql.yml` uploads from the `CodeQL (actions)` and `CodeQL (javascript-typescript)` jobs, so it depends on that workflow staying on and on CodeQL default setup staying off (see "Keeping CodeQL default setup off" above). It is not a status check and is not one of the required checks. Dismiss a false positive with a reason in the repository's **Security** tab, never by lowering the thresholds: a lower threshold lets every alert of that severity through, not only the false one. On 2026-11-17, before the rule was added, the three open alerts were dismissed that way: one false positive in `src/lib/api/keys.ts` and two used in tests. Check with `gh api repos/eddiejaoude/StackDash/rules/branches/main --jq '.[] | select(.type == "code_scanning") | .parameters'`: it must show `{"code_scanning_tools":[{"alerts_threshold":"errors","security_alerts_threshold":"high_or_higher","tool":"CodeQL"}]}` (it did on 2026-11-17).
- Keeping `dependabot[bot]` on the CLA Assistant allowlist for this repository. `license/cla` is a required check and Dependabot cannot sign the CLA, so without the entry every Dependabot pull request, version or security update, waits on a check that never passes. CLA Assistant documents adding bot users by name in its dashboard ("Can I allow bot user contributions?" in its README). Its public API does not show the allowlist (`getLinkedItem` for this repository returns only the gist), so on 2026-11-16 the entry was unverified. Check that the first Dependabot pull request shows `license/cla` passing with `gh pr checks <number> -R eddiejaoude/StackDash`.
- Checking the issue chooser after the contributor templates in `.github/ISSUE_TEMPLATE/` reach `main`. GitHub reads issue templates from the default branch only, so no branch before that can show them. On the repository, open **Issues**, then **New issue**: the chooser must list **Bug report**, **Adapter request**, and **Task**, and one **Report a security vulnerability** row that opens the security policy. GitHub may add its own row of that name once `SECURITY.md` is on `main`. If both show, remove the `contact_links` entry from `.github/ISSUE_TEMPLATE/config.yml`: it duplicates GitHub's row.
- Keeping the CI workflow on, because `CONTRIBUTING.md` tells contributors that CI runs on every pull request and the ruleset requires its checks. Check with `gh api repos/eddiejaoude/StackDash/actions/workflows --jq '.workflows[] | {name, state}'`: CI must show `"state": "active"`. If it shows `"disabled_manually"`, run `gh workflow enable ci.yml -R eddiejaoude/StackDash`.
- Approving the first workflow run on a first-time contributor's pull request from a fork, after reading the diff. The fork approval policy is `first_time_contributors` (`gh api repos/eddiejaoude/StackDash/actions/permissions/fork-pr-contributor-approval`), so CI and the four required checks wait on that approval.
